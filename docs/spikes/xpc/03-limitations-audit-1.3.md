I explored both trees, ran read-only `container` commands against the live 1.3.0 runtime, and traced every row. One gating fact first, because it decides most verdicts.

## The fact that unlocks everything

`/Users/michael/local/apple-container/Sources/ContainerXPC/XPCServer.swift:176-192` — the apiserver's **only** authorization check on an inbound XPC message is:

```swift
xpc_dictionary_get_audit_token(object, &token)
let clientEuid = audit_token_to_euid(token)
guard clientEuid == serverEuid else { … "unauthorized request" }
```

No code-signing check, no entitlement check, no team-ID check. Any process running as the same user can `xpc_connection_create_mach_service("com.apple.container.apiserver")` and drive it. Routes are plain strings under key `com.apple.container.xpc.route` (`XPCMessage.swift:24`), payloads are `Data` holding **Codable JSON** of public structs, errors are JSON under `com.apple.container.xpc.error`, and fds ride as `xpc_dictionary_set_fd`. A .NET P/Invoke client over `libxpc` is entirely viable (cider already has `src/Cider.AppleContainer/Native/Libc.cs`). Route list: `Sources/Services/ContainerAPIService/Client/XPC+.swift:148-191`; registration: `Sources/APIServer/APIServer+Start.swift:293-309`.

Note also `XPCRoute.containerEvent` (`XPC+.swift:162`) is **declared but never registered** — there is no event stream to subscribe to; polling stays necessary.

Timing check: `container ls -a` costs ~20–40 ms wall. CLI spawn is *not* a big tax; the win from XPC is capability and process-model, not latency.

## Beyond the table

### (1) Held `container start -a` children — does XPC remove the need?

**Yes, completely.** `container start -a` holds a child only because the *CLI* creates the pipes: `ProcessIO.create(tty:interactive:detach:)` allocates `Pipe()` for stdout/stderr only when `detach == false` (`ProcessIO.swift:45-120`), and `ContainerStart.swift:80-105` then blocks in `io.handleProcess`. With `detach: true` it passes `nil` fds, calls `process.start()`, closes, and exits — the container keeps running with no parent.

Over XPC cider does the same thing but keeps the fds: `containerBootstrap(id, stdio:[fd0,fd1,fd2], dynamicEnv)` where the three fds are pipes (or a PTY master, cider already has `PtySyscalls.cs`) that **the daemon itself owns** → `containerStartProcess(id, id)` → `containerWait(id, id)` for the exit code. Ownership of the container's lifetime moves from "a subprocess cider must not lose" to "a socket cider can reconnect". Consequences:

- No orphan class exists, so `OrphanReaper` (`AppleContainerRuntime.cs:100-107`) and the whole "hard-killed daemon wedges the runtime" troubleshooting section become obsolete — the network-holding debris came from CLI children, not from containers.
- The apiserver already owns exit tracking regardless: `exitMonitor.track(id:waitingOn:)` at `ContainersService.swift:527-545`, firing `handleContainerExit` which stops the runtime helper and marks `.stopped` (`:993-996`).
- Everything is still teed to `stdio.log` by the runtime's `MultiWriter` (`RuntimeService.swift:241-258`), so cider gets *both* live pipes and a durable file — belt and braces.
- Remaining gap: if the container exits while cider is down, `handleContainerExit` has already nulled the runtime client, and no exit code is persisted anywhere. `containerWait` after the fact fails.

This is, in my view, the single most valuable item in the whole report.

### (2) "Every container is a VM" — does 1.3 help? Do container machines help?

**Container machines do not help, and I can say that categorically from the source.** `MachinesService.toContainerConfig` (`Sources/Services/MachineAPIService/Server/MachinesService.swift:642-706`) builds a **single ordinary `ContainerConfiguration`** and creates it through `ContainerClient()` (`:48,76`). A machine *is* one container in one VM, differing only in: it runs the image's `/sbin/init`, mounts your `$HOME` over virtiofs, `capAdd:["ALL"]`, `maskedPaths:[]`, `readonlyPaths:[]`, `ssh:true`, optional `virtualization`. There is **no nested container runtime inside it** — `docs/container-machine.md` positions it as "a Linux environment", and its examples are `systemctl start postgresql`, not `docker run`.

So: **container machines cannot host multiple containers, and they do not change `container run` boot time at all** — `container run` still creates and boots its own VM through the same path. The only indirect angle is that a machine created with `--virtualization` on M3+ with a KVM kernel could run a nested Docker/Podman, which is a fundamentally different product than cider.

**What `container run` boot time is actually dominated by**, per `RuntimeService.bootstrap` (`:136-330`):
1. `ServiceManager.register` — launchd spawns a *fresh* `container-runtime-linux.<id>` process per container (`ContainersService.swift:433-439`).
2. `VZVirtualMachineManager(kernel:initialFilesystem:rosetta:)` (`RuntimeService.swift:175-180`) boots a VZ VM with the configured kernel — default per `[kernel]` in `docs/container-system-config.md`, bumped in 1.3 to a **Kata Containers 3.32.0 *debug* build** (`d6de569`) — plus the vminit initfs (`ghcr.io/apple/containerization/vminit:0.34.0`, `container-system-config.md:43-44`).
3. `vminitd` comes up inside and the host handshakes with it.
4. Network allocation per attachment, an XPC round-trip to the vmnet plugin each (`:186-215`).
5. rootfs ext4 block attach (cloned at create time, `Bundle.swift:90-105`).

None of that is affected by talking XPC instead of spawning the CLI — the CLI is a ~20–40 ms tax on a multi-hundred-ms VM boot. 1.3 offers **nothing** that amortises the per-container VM. `docs/technical-overview.md:60-64` additionally warns that guest memory freed inside the VM is never returned to macOS, so long-lived services accumulate RSS until restarted — worth adding to cider's README, it bites Compose users.

Also worth correcting in the README: Apple's per-container defaults are **4 CPUs / 1 GiB** (`ContainerConfiguration.swift:166-168`, `container-system-config.md:87-92`); the 2 CPU / 2 GiB figure is cider's own (`CiderOptions.cs:56,59`).

### (3) `docs/` skim — 1.3 features cider does not use yet

`docs/` was refactored in 1.3 (`875d80b`). 17 files. What's there that cider isn't exploiting:

- **`runtime-configuration.md`** — `--masked-path`/`--read-only-path` incl. the `NONE` sentinel (cider uses these), `--virtualization` for nested KVM (**unused** — the real DinD answer), `--init` (used), **`--init-image`** (**unused**: a custom initfs could host cider-side agents *inside* the VM before the OCI process starts — an interesting lever for in-guest DNS or a log shipper).
- **`resource-usage.md`** — `container stats --format json` fields (cider uses), documented over-commit policy, `container system df` (worth wiring to `/system/df`), `container volume prune` / `image prune --all`.
- **`ulimits.md`** — `--ulimit` (cider uses).
- **`host-integration.md`** — `--ssh` agent forwarding (**unused**; would make `docker build --ssh` and private-repo clones work, and 1.3 added it to the *builder* too, `e87d3a0`), and the `dns create --localhost` + pf recipe discussed above.
- **`networking.md`** — `--network <name>,mac=…,mtu=…` (**mac/mtu unused**), `[::1]` publish syntax (**unused**), `--subnet-v6` (**unused**), and an explicit upstream warning (`networking.md:70-82`, apple/container#1809) that **bare-hostname service discovery on custom networks does not work** — which is precisely why cider runs its own CoreDNS, and is worth citing in cider's README as vindication.
- **`container-machine.md`** — covered above; not useful to cider.
- **`command-reference.md`** — flags in the CLI that cider's `ArgBuilder` never emits: `--rosetta`, `--virtualization`, `--ssh`, `--no-dns`, `--dns-domain`, `--kernel-arg`, `--init-image`, `--runtime`, `--cidfile`, `--os`/`--arch`.
- **XPC-only fields with no CLI flag at all** (from `ContainerConfiguration` vs `Utility.swift:190-328`) — these are pure XPC wins and are *not* in cider's limitations table:
  - **`sysctls`** (`ContainerConfiguration.swift:34`) — never set by the CLI. Docker's `HostConfig.Sysctls` becomes honourable. Elasticsearch/Redis Testcontainers set these.
  - **`stopSignal`** (`:64`) — CLI only copies it from the image (`Utility.swift:260`); XPC lets cider honour Docker's `--stop-signal`.
  - **`AttachmentOptions.hostname`** — CLI forces the container id (`Utility.swift:314-328`); XPC gives real `--hostname` support.
  - **`ContainerCreateOptions.rootFsOverride`** — pre-seed a rootfs, which is the clean fix for the `docker cp`-into-created hack.

## Ranked: what to remove first (impact × ease)

1. **Talk XPC for the container lifecycle — kill the held children.** Removes the orphan-reaper, the whole "hard-killed daemon wedges the runtime" failure class, and most of the exit-code loss in one change. Everything below rides on the same client. Impact: highest. Ease: medium (one `libxpc` P/Invoke layer + a JSON mirror of `ContainerConfiguration`, whose decoder is defensively `decodeIfPresent` everywhere).
2. **`docker history` per-layer sizes.** Cider already reads the manifest; add `layers[].size` and walk it against `history[]`. ~30 lines, zero risk, and it deletes a README row outright.
3. **Delete the stale `ExposedPorts` row from the README.** `RecoverExposedPortsAsync` already fixed it; the docs are lying about a limitation that no longer exists.
4. **IPv6 surfacing.** The address is already parsed and thrown away (`ContainerModels.cs:195` → `RuntimeModels.cs:40`). Plumbing it to `GlobalIPv6Address` is small and immediately visible in `docker inspect`.
5. **`network_mode: none` via `networks: []`.** One field on the XPC create path, turns a 400 into working behaviour for a real Compose pattern.
6. **`sysctls`, `stopSignal`, `hostname`** over XPC. Three fields the CLI structurally cannot express; each unblocks specific Testcontainers/Compose workloads. Free once item 1 lands.
7. **`containerLogs` fds instead of `container logs`.** Foreign-container logs, boot logs, no subprocess. Accept that stdout/stderr stay merged for containers cider didn't start.
8. **`host.docker.internal` → `127.0.0.1` via a pf anchor.** High user impact (loopback-binding dev servers are the common case) but needs root and carries Apple's own documented Private Relay caveat — gate it behind a flag.
9. **BuildKit via `containerDial` + `Builder.proto`.** Highest ceiling of anything here, but it is a Control↔Builder adapter, i.e. weeks. Correct the README's "no-go / private Swift-only XPC" claim now regardless — it is wrong and it is steering the roadmap.
10. **A read-only ext4 reader for stopped rootfs.** Fixes `cp` out, `HEAD archive`, and the symlink note together, at O(path). Real work; do it only if those paths show up hot.

Not worth attempting: pause/unpause, `--network host`, `container:*`, static IPs, multi-attach volumes, `diff`, native restart/health, volume drivers, and any per-container VM cost reduction. Each is blocked by a structural property of one-VM-per-container, not by the CLI.
